# 06 — Phase 1 Migration Plan: Flask → Next.js Portal

## Scope

Stand up the rmdig-ai portal at `app.rmdig.ai` as a Next.js application with three working capabilities:

1. **Authentication** — email/password + OAuth login, sessions, role-based workspace shell
2. **Device linking** — one-time claim-token flow between portal and AvApp (per [01_accounts_and_orgs.md](01_accounts_and_orgs.md))
3. **SAR org onboarding** — registration form, document submission, RMDig operator review queue, approval workflow, member invitations

**Explicitly out of scope for Phase 1:**
- Capture review queue (depends on SnowDB existing)
- Stripe Connect / payouts (Phase 4)
- Alert dispatch UI (depends on AvServ A3 milestone)
- Movement tracking, follow-up reports (depends on alert dispatch)
- Marketing-site migration (current Flask site at `rmdig.ai` stays untouched)

The Flask app continues to serve `rmdig.ai` (marketing, signup forms). The new Next.js app serves `app.rmdig.ai` (portal). Subdomain-level split; no DNS surgery to the existing site.

## Tech stack decisions

| Concern | Choice | Why |
|---|---|---|
| Framework | **Next.js 15 (App Router) + React 19** | Server actions, RSC, mature ecosystem. The standard Next.js story. |
| Hosting | **Vercel** | Best-in-class Next.js DX. Marketing stays on Render; only `app.rmdig.ai` points at Vercel. |
| Database | **Postgres on Neon** (with PostGIS extension) | Branching for dev environments. PostGIS supported. Reasonable pricing. SnowDB later can use the same provider with a separate project. |
| ORM | **Drizzle ORM + Drizzle Kit migrations** | SQL-first, lightweight, works cleanly with PostGIS via raw SQL escape hatches. Prisma's PostGIS story is painful. |
| Auth | **Auth.js v5 (NextAuth)** with Drizzle adapter | Self-hosted, session-based, supports email/password + OAuth + MFA plugins. Clerk would be faster setup but more lock-in and per-user cost — wrong tradeoff for a SAR/safety platform handling sensitive context. |
| Styling | **Tailwind v4** + **shadcn/ui** primitives | Existing site already uses Tailwind classes; v4 is the proper PostCSS pipeline. shadcn for accessible primitives without lock-in. |
| Forms | **React Hook Form + Zod** | Standard combo, server-action friendly, strong types end-to-end. |
| Maps | **MapLibre GL** + a polygon-draw plugin (e.g., Terra Draw) | Needed for SAR region polygons. OSM or MapTiler base layer. Free / cheap at this scale. |
| Email | **Resend** | Modern transactional email; good DX; affordable. Used for verification, claim tokens, approval notifications. |
| Logging / errors | **Sentry** for errors; structured `pino` logs to Vercel | Standard for production debugging. |
| Background work | **Skip for Phase 1.** Use Vercel cron for the few periodic jobs (claim token expiry, etc.) | Inngest / Trigger.dev can come in Phase 4 when payout period close needs proper queuing. |

**Decision needed: new repo or add to current?**

- **New repo** (`rmdig-portal` or similar): clean separation, can deploy independently, doesn't risk breaking the live Flask site. Recommended.
- **Same repo, new directory** (`rmdig-ai/portal/`): single source of truth, easier cross-reference. Risk: Vercel build accidentally picks up Flask files; harder to give different deployment targets cleanly.

Recommend a **new repo** (`rmdig-portal`). The marketing-site → portal migration in Phase 5+ can fold them back together or move marketing into the Next.js app at that point.

## Authentication

### Provider config (Auth.js)

- **Credentials** (email + password) with bcrypt hashing, server-side rate limiting via Upstash Redis or simple table-based throttle.
- **Google OAuth** for low-friction signup.
- **Apple OAuth** (deferred — Apple requires a $99/yr Apple Developer account and signing key setup; reasonable for v1.1).
- **Email verification required** before any state-changing action (creating SAR org, linking device).
- **Session storage**: database sessions via the Drizzle adapter, 30-day expiry, rolling refresh.

### MFA

- TOTP via Auth.js's experimental MFA support or a small custom layer; recovery codes generated at enrollment.
- **Mandatory for all users at public launch.** Enforced via middleware: any session for an unenrolled user is redirected to `/settings/mfa/enroll` before reaching any other portal route. Rationale: contributor and SAR-org accounts will have payouts attached, so account takeover is a direct financial-impact event.
- During development and internal soft launch (P1.5), MFA is optional with a banner urging enrollment. The mandatory gate flips on at public launch (post-Phase 1).
- `rmdig_admin` and `rmdig_reviewer` roles require MFA from day 1, even during internal launch — these accounts approve SAR orgs and capture data, so they're high-value targets even before money flows.

### Permissions

A single helper `lib/permissions.ts` exposes:

```typescript
canAccessRmdigAdmin(user): boolean
canManageOrg(user, orgId): boolean
canRespondForOrg(user, orgId): boolean
canLinkDevices(user): boolean           // any verified user
```

Route group layouts call these in their server-side `layout.tsx` and redirect on deny. Server actions re-check independently — never trust the layout to gate writes.

## Device linking flow

### Sequence

```
┌──────────────────────────────────────────────────────────────────────┐
│ Portal (app.rmdig.ai)         │ AvApp (Flutter)      │ AvServ (Go)   │
├──────────────────────────────────────────────────────────────────────┤
│ User clicks "Link a device"   │                      │               │
│ Server action:                 │                      │               │
│   - generate claim_token       │                      │               │
│   - insert device_claim_tokens │                      │               │
│     (expires_at = now+5min)    │                      │               │
│   - return token + QR data URL │                      │               │
│ Display QR + alphanumeric code │                      │               │
│                                │ Settings → "Link to  │               │
│                                │  account" → scan QR  │               │
│                                │  or type code        │               │
│                                │ POST /api/device-    │               │
│                                │  link/consume        │               │
│                                │  { claim_token,      │               │
│                                │    device_jwt }      │               │
│ /api/device-link/consume:      │                      │               │
│   1. validate claim_token      │                      │               │
│      (exists, unexpired,       │                      │               │
│       unconsumed)              │                      │               │
│   2. verify device_jwt         │                      │               │
│      (signature against        │                      │               │
│       AvServ public key)       │                      │               │
│   3. S2S call to AvServ:       │ ───────────────────► │ PATCH         │
│      "set user_id on device"   │                      │ /v1/internal/ │
│                                │                      │  devices/:id  │
│                                │                      │  { user_id }  │
│   4. on AvServ 200:            │ ◄─────────────────── │ 200 OK        │
│      - mark claim_token        │                      │               │
│        consumed                │                      │               │
│      - insert device_links     │                      │               │
│      - return 200              │                      │               │
│                                │ Show "Linked to      │               │
│                                │  user@email"         │               │
└──────────────────────────────────────────────────────────────────────┘
```

### Endpoint contracts

**Portal-internal (used by the portal's own UI):**

```
POST /api/device-link/claim
  Auth: portal session (verified user)
  Returns: { token: string, qr_data_url: string, expires_at: ISO8601 }
```

**Portal-public (called by AvApp):**

```
POST /api/device-link/consume
  Headers: none (auth happens via included device JWT)
  Body: { claim_token: string, device_jwt: string }
  Returns: { user_email: string, linked_at: ISO8601 }
  Errors: 400 (token invalid/expired), 401 (device JWT invalid),
          409 (token already consumed), 502 (AvServ unreachable)
```

### What AvServ needs to add (cross-repo dependency)

- An S2S endpoint `PATCH /v1/internal/devices/:id` callable with a peer JWT, body `{ user_id }`. Idempotent.
- A documented public key (or JWKS endpoint) the portal can use to verify device JWTs without a round-trip.
- Decision needed: does the portal verify device JWT locally, or call an AvServ verify endpoint? Recommend **local verification** — keeps the device-link flow snappy and avoids an additional dependency on AvServ uptime for portal logins.

File an issue against AvServ to add this. Phase 1 can proceed in parallel with AvServ work as long as the device-link endpoint is stubbed against a mock AvServ for testing.

## SAR org onboarding flow

### State machine

```
[draft] ──submit──► [pending] ──approve──► [approved] ──suspend──► [suspended]
                       │                       │                       │
                       └──reject──► [rejected] │                       │
                                               └──appeal──► [pending]  │
                                                                       │
                       reactivate ◄──────────────────────────────────┘
```

`status` field on `sar_orgs` enforces the machine. Transitions are logged in a separate `sar_org_status_log` table (append-only, mirrors the audit pattern from [05_ledgers.md](05_ledgers.md)).

### Submission form

Fields collected on org creation:

1. **Org identity:** name, public-facing description, primary contact (name + email + phone)
2. **Service area:** drawn polygon on a MapLibre map; stored as PostGIS `geography(polygon, 4326)`
3. **Operating status:** dropdown (county SAR / state SAR / 501(c)(3) / nonprofit / volunteer group / other) + free text
4. **Proof of operating status:** file upload (PDF or image) — county registration letter, 501(c)(3) determination letter, etc. Stored in object storage (Vercel Blob for Phase 1 simplicity; can move to S3 later).
5. **Acknowledgments:** checkboxes for the SAR org TOS items in [04_payments_and_legal.md](04_payments_and_legal.md).

On submit: row inserted with status `pending`, creator user assigned `admin` role on the org via `org_memberships`, email sent to all `rmdig_admin` users + the submitter (confirmation).

### Operator review queue

`/admin/sar-approvals` (gated to `rmdig_admin` and `rmdig_reviewer`):

- Table of all `pending` orgs with: name, region (small map preview), submitter, submitted_at, operating status, link to proof doc.
- Per-row actions:
  - **Approve** → status → `approved`, send notification email to org admin, unlock org workspace.
  - **Request changes** → free-text note → status stays `pending`, email to submitter with the note.
  - **Reject** → reason dropdown + free text → status → `rejected`, email to submitter.

All actions write to `sar_org_status_log` with actor user and timestamp.

### Member invitation

Once approved, org admin can invite members via `/sar/[orgId]/members`:

- Enter email + role (responder by default; admin requires confirmation).
- Insert `org_invitations` row with random token (TTL 14 days), send invite email via Resend.
- Invite-accept landing page: `/invite/[token]` — if signed in, accepts immediately; if not, walks through sign-up then accepts.
- On accept: insert `org_memberships`, mark `org_invitations.acceptedAt`, drop the user into the org workspace.

## Decisions made before starting

1. **New repo** — `rmdig-portal` on GitHub, separate from the current Flask `rmdig-ai` repo.
2. **Both OAuth and email/password** — Google OAuth + credentials provider from day 1. Some SAR responders won't have or want a Google account; email/password is the inclusive default.
3. **Vercel Blob for proof-doc uploads** in Phase 1 (zero setup). Migrate to R2/S3 later if scale or cost demand it.
4. **MFA mandatory for all users at public launch.** Optional with strong-push banner during dev and internal soft launch. `rmdig_admin` / `rmdig_reviewer` roles require MFA from day 1. See MFA section above for full enforcement model.
5. **Marketing site folds into Next.js in Phase 5+** with a major refactor permitted — current Flask templates are content-heavy but structurally simple; they'll likely become Next.js pages or MDX with a refreshed component system rather than a 1:1 port. Phase 5 will retire the Flask app entirely.

## Success criteria

Phase 1 is done when:

- [ ] You can sign up, verify email, log in, and reach a dashboard at `app.rmdig.ai`.
- [ ] You can link an AvApp device to your account via the QR/code flow, and AvServ reflects the user_id on the device row.
- [ ] An external user can submit a SAR org application, you can approve it from the admin queue, and the new org admin can invite a responder.
- [ ] All flows have email notifications (verification, claim confirmation, org approval, invite).
- [ ] MFA works for at least your own account.
- [ ] Sentry catches errors and structured logs are queryable in Vercel.
- [ ] The marketing site at `rmdig.ai` is untouched and still serving.

Once these are green, Phase 2 (SnowDB + capture review queue) becomes the next focus. See [00_platform_architecture.md](00_platform_architecture.md) for the broader migration sequence.
